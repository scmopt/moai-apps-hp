# Grilling

ユーザーの計画・設計・意思決定を、**共通理解に達するまで容赦なくインタビューする**ためのスキル。
目的は「気持ちよく合意すること」ではなく、**黙って仮定されている前提をゼロにすること**。

## 中核となるモデル：設計ツリー

設計は木構造をなす。1つの決定は、その下にぶら下がる複数の決定へ枝分かれする。
上位の決定が決まらないと、下位の決定は問うても意味がない（回答を推測することになる）。

**フロンティア（frontier）** = 前提となる上位の決定がすでに確定していて、**いま聞ける**質問の集合。

## 手順

### 1. ラウンド単位で、フロンティア全体をまとめて聞く

- **フロンティア上の質問は、1ラウンドでまとめて提示する**。小出しにしない。
- 各質問に **番号を振る**（Q1, Q2, ...）。
- 各質問には **必ず自分の推奨回答を添える**。ユーザーが迷う論点でも議論が前に進むようにするため。
- 提示したら **ユーザーの回答を待つ**。勝手に次へ進まない。

### 2. 依存関係を守る

同じラウンド内の未解決の質問に答えが依存する質問は、**このラウンドには属さない**。後のラウンドに送る。

### 3. 回答のたびにツリーを組み直す

回答が返ってきたら設計ツリーを再構成し、**フロンティアを再計算**してから次のラウンドを出す。
回答によって枝ごと消えることもある（その質問はもう聞かない）。

### 4. 事実調査は自分の仕事、決定はユーザーの仕事

- フロンティア上の質問が、環境から分かる事実（ファイルの中身、既存実装、依存ライブラリ、データの形など）を必要とするなら、**サブエージェントを起動して自分で調べる**。
- **自分で調べられることをユーザーに聞かない。**
- ただし **調査でブロックしない**。実行中の調査は「未確定の前提」なので、その下流の質問だけが待ち、**残りのフロンティアは今すぐ聞く**。

### 5. 終了条件

**フロンティアが空になったらセッション終了**。＝設計ツリーの全枝を訪問し、黙って仮定されたものが残っていない状態。

**ユーザーが「共通理解に達した」と確認するまで、実装に着手しない。**

## 出力フォーマット

```
❓ **Q1** - **<質問のタイトル>**: <質問本文。複数段落でも、選択肢の列挙でもよい>

➡ <推奨する回答>

---

❓ **Q2** - **<質問のタイトル>**: <質問本文>

➡ <推奨する回答>
```

## 質問の切り口（枝を見落とさないためのチェックリスト）

- **スコープ**：何を作らないのか。どこまでが今回の範囲か。
- **前提**：暗黙に仮定している入力・環境・利用者は何か。それは検証済みか。
- **代替案**：なぜこの方式なのか。却下した案と却下理由は何か。
- **境界条件**：ゼロ件・重複・欠測・巨大入力・同時実行のときどうなるか。
- **失敗時**：失敗したらどうなるか。誰が気づくか。ロールバックできるか。
- **既存資産との整合**：既にあるコード・データ・命名規約とどう噛み合うか。
- **検証方法**：「うまくいった」をどう測るか。テストは何を通せば十分か。
- **不可逆性**：後から変えにくい決定はどれか。それは今決める必要があるか。
- **コスト**：時間・計算・運用負荷の見積もりは。割に合うか。

## やってはいけないこと

- 質問を1問ずつ小出しにして、ラウンド数を無駄に増やす。
- 推奨回答を省いて「どうしますか？」とだけ投げる。
- ユーザーの回答を待たずに次のラウンドや実装へ進む。
- 自分で調べられる事実をユーザーに質問する。
- 曖昧な合意のまま「では実装します」と切り上げる。
